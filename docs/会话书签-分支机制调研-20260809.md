# 会话书签 / 任意轮分支 · DSH 机制调研（2026-08-09）

> 调研对象：DSH 快照 260808（test-csyangwen checkout，commit 7688da9c）
> 调研问题：官方为什么只在「最后一个已完成回合的 AI 回答尾部」提供「在新对话中分支」？
> 为什么用户输入下面没有重试/编辑按钮？AI 回复下面没有重试按钮？这是存储机制的问题，还是产品决策？

---

## 一、结论摘要（TL;DR）

**不是"存储做不到"，而是三层因素叠加：**

1. **存储层：事件溯源 + append-only**——会话日志是 `SessionEvent` 事件流（唯一事实源），flush 后的事件**永不重写**；崩溃恢复靠"关闭未完成轮次"而非截断。原地"重试/编辑"= 改写或截断已持久化历史 → 破坏日志不变式，官方不支持。
2. **轮次不变式：fork 种子必须结束于"已关闭的轮次"**——fork = 复制连续事件前缀作为子会话种子；边界落在打开的轮次中间会被 `_forkSeed` 直接拒绝（"ends inside open turn"）。用户消息总在打开的轮次里、AI 回复中间有未关闭的 step/工具调用，都不是合法边界。
3. **产品语义：官方明确做过三轮决策**——曾放"用户消息编辑按钮"（无功能 stub，已移除）、曾放"用户气泡分支按钮"（语义误导，已移除）。"从我的消息处分支"实际切在该轮 turn/end（把下面的回答也带走），与"分叉重问"直觉相反；真正"重问"的正确语义 = **切在消息之前 + 预填输入框**，官方决策文档明说这是**预留但未实现**的 Host 操作。

**对「会话书签」功能的决定性结论**：
- 底层 API **完整支持任意已完成轮次的 fork**：`SessionStore.fork(boundary)`（core）→ Host RPC `session.fork({ atSeq })` → client contract `sessions.fork({ atSeq? })`。**限制全部在 UI 策略层，插件可以绕过。**
- 用户想要的"每轮打标签 + 跳转创建分支"在技术上**完全可行**（见第四节方案）。

## 二、官方现状：有什么 / 没有什么

### 有的
- **「在新对话中分支」按钮**（`MessageItem` 的 IconActions 行：复制 / 时钟 / 分支）——仅出现在**已完成回合的、有文本内容的最后一条 assistant 回答**下方，且**仅当该消息就是最后一个已完成回合的尾部**时才启用；否则可见但 `aria-disabled`（tooltip 解释原因）。
- **Session 行操作 fork**：左侧会话列表行上可 fork（取"最新已完成轮次"）。
- **fork 会继承**：cwd、parentSession、模型/提供方/reasoning 配置（发布前由 Host 从日志安装），子会话 seed 深拷贝。

### 没有的
- **用户消息编辑**：曾有过按钮（stub，无任何行为），2026-07-31 移除。
- **用户消息下分支**：曾有过按钮，2026-08-06 移除（详见下文决策链）。
- **AI 回复"原地重试"**（当前会话内重新生成该条回复）：不存在。等价物 = 分支到新会话，或再发一条消息。
- **从任意轮分支的 UI 入口**：UI 不提供（但 API 支持）。

## 三、机制详解

### 3.1 存储：事件溯源，append-only

- 持久化单位就是 `SessionEvent`（`packages/session-persistence` README 原话："The persisted unit IS the existing SessionEvent (event-sourced model — the log is the single source of truth)"）。
- `append`：append-only；首个事件 seq 必须等于存储的下一个 seq；**flush 后的事件永不重写**；崩溃时"关闭未完成的轮次"（补合成 `tool/result`/`step/end?`/`turn/end {interrupted}`），**绝不截断**（"A crashed turn is closed, not truncated"）。
- 日志结构：`turn/start → (user message / step/start → assistant 节点 / 工具调用与结果…) → turn/end` 的嵌套事件流；seq 连续，中段 seq 缺口直接拒绝加载。

**推论**：任何"改写历史"的操作（编辑已发送消息、原地重新生成某条回复）都要求重写或截断已 flush 的日志——与事件溯源模型根本冲突。官方选择的是"**日志只增，历史不可变，变化=新分支（新会话）**"。

### 3.2 fork 原语与轮次边界（core/session）

`SessionStore.fork(source, boundary?, childSessionId?)`（`packages/core/session/src/index.ts`）：

- `boundary` = 复制到的源事件 seq（含该序号）；省略 = 当前最后一个事件。
- `_forkSeed` 校验链：
  - boundary 必须是存在的、连续的 seq；
  - **拒绝"ends inside open turn"**——即所选前缀的最近轮次边界不能是未匹配的 `turn/start`。
- 也就是说：**合法 fork 种子 = 连续事件前缀 + 结束于已关闭轮次**（可以结束于 `turn/end` 之后的独立事件，但不能在轮次中途）。

**为什么用户消息处不行**：用户消息事件必然位于 `turn/start` 之后（轮次已打开），复制到用户消息 = 前缀结束于打开的轮次 → 非法。**为什么 AI 回复中途不行**：回复可能在未结束的 step 内、或带悬空工具调用 → 非法。**为什么 AI 回复尾部可以**：该轮 `turn/end` 已关闭 → 合法。

### 3.3 Host RPC 的锚点策略（fork-api 决策文档）

Host 的 `session.fork` RPC 接受 `atSeq`，**把它当作"所需轮次内的锚点"而非存储边界**：

- 选择该锚点处**或其后的首个 `turn/end`**；
- 锚点省略或超过末尾 → 选最后一个已完成轮次；
- 锚点存在但从该锚点起找不到 `turn/end` → 返回 `fork-unavailable`，**绝不回退到更早轮次**（不静默遗漏用户点击的消息）。

**推论**：消息级 fork 的粒度 = 轮次。你点任何一条消息，实际分支点都是"它所在轮次的 turn/end"——分支出来的一定是"该轮完整结束"的语义。

### 3.4 client contract：插件可用的 fork API

`packages/client/runtime/src/client/contract/sessions.ts`：

```ts
fork(opts: { sessionId: SessionId; atSeq?: number; increaseTitle?: boolean }): Promise<SessionId>
```

- `atSeq` 可选：省略 = 最新已完成轮次；传值 = 锚定到该 seq 所在轮次的 turn/end。
- 成功后合并子会话到摘要列表，返回子会话 id。

## 四、对「会话书签」功能的可行性结论与方案

### 4.1 结论

1. **"从任意已完成轮次创建分支"官方 API 层完全支持**（client `sessions.fork({ atSeq })` / Host `session.fork` / store `fork(boundary)`），官方只是**没有在 UI 上暴露历史轮次的入口**。
2. **"原地重试/编辑"在事件溯源下不可行也不该做**——官方模型就是"变化 = fork 新会话"。
3. 用户想要的"每轮打标签 + 界面可见 + 随意跳转创建分支"= **对每个已完成轮次提供 fork 入口 + 书签标记**。语义与官方分支完全一致（fork 出新会话），只是入口从"最后一条回答"扩展为"任意已完成轮次"。

### 4.2 插件实现方案（候选，按侵入度排序）

**方案 A：纯客户端 DOM 注入（最贴合 dsh-ui-settings 已验证模式）**
- 每轮已完成回合的 assistant 回答尾部注入「📌 书签 / 分支」按钮（MutationObserver 保活）。
- 点击 → 调 client fork API（需确认插件 client 侧能否拿到 api 连接 / RPC 通道——见待验证点）。
- 需要从 transcript DOM 推断轮次边界（`turn/end` 对应哪个气泡）——官方有 `ConversationSnapshot.turnEnds`，但插件 DOM 层拿不到内部 store，需自行从 DOM 结构推断或走宿主 API。

**方案 B：宿主 API 代理（host 侧注入 `ctx.sessions` 服务）**
- 插件 host 侧新增 HTTP API：`POST /api/session-bookmarks/fork { sessionId, atSeq }` → 内部调 `ctx.sessions.fork(source, boundary)`（插件可注入 `sessions` 服务）。
- 书签数据落盘 `<memoryDir>/bookmarks.json`：`{ sessionId, label, atSeq, createdAt }`。
- 客户端：书签面板（列出某会话全部书签 + 标签）+ DOM 注入入口。
- **优点**：不依赖 client 内部 API，宿主侧 `sessions` 服务就是官方 fork 原语；书签持久化可跨会话复用。

**方案 C：先做"每轮分支入口"最小版（不做书签面板）**
- 一期只验证核心需求：给每个已完成轮次的回答尾部注入「在此分支」按钮（DOM 注入 + 宿主 fork API）。
- 二期再加：书签命名 / 书签列表 / 跳转。

### 4.3 待验证点（开工前）

1. 插件 client 侧（ui-slots 槽位 / DOM 增强）能否直接拿到 `api.sessions.fork`，还是必须走宿主 HTTP 代理 → 决定方案 A/B。
2. 插件 host 侧注入 `sessions` 服务是否可行（`export const inject` 声明 + cordis 服务依赖关系）。
3. 从 DOM 推断"已完成轮次的回答尾部"的稳定锚点（官方组件结构：`MessageItem` IconActions 行、turn-end 判定）——需 headless 实测 DOM。
4. fork 出的子会话标题递增（`increaseTitle`）与打开子会话的体验。
5. 书签数据与 fork 失败（如会话已被删除/轮次被新分支覆盖）的容错。

## 六、插件 fork 实现审查结论（2026-08-09 补充）

用户已实现书签 fork（`lib/bookmarks.js` `buildForkSeed`/`forkSession` + `src/client/bookmark-injector.tsx` 接管中间轮官方 Branch 按钮），逐行对比官方 `api-proxy.ts` fork RPC（260808 快照）：

- **算法层完全一致**：锚点逻辑（`atSeq` → 首个 `>= atSeq` 的 turn/end；省略/超尾 → 最后一个 turn/end；目标轮未完成 → 拒绝）与"顺延吸收 turn/end 后 OOB 事件到下一个 turn/start"的细节都与官方相同（官方用 `findLast`，插件用 `reverse().find`，等价）。
- **差异 P1**：官方创建子会话传 `agentOptions: agentOptions()`（默认 provider/model 兜底）+ `setup: installTarget`（Web 层 LLM target 派生）；插件只传 sessionId/seed/meta。理论风险：agent-loop `buildRequest` 在 route 为空且无 `agent/request` 中间件兜底时 throw `"agent has no provider/model"`（`agent-loop/src/agent.ts:420`）；且未装 installTarget 时子会话模型不继承源会话（官方靠 seed 日志 request/header 事件派生）。**实测排除**：用户当前会话即过往轮次 fork 产物，运行正常（环境有兜底/默认）。
- **差异 P2**：workspace attach 失败官方返回 `workspace-attach-failed` 错误码，插件只 console.warn（子会话可能不在左侧列表显示）。
- **差异 P3**：subagent 源会话的 workspace 归属官方找"最近 owning ancestor"，插件按 cwd `resolveByPath`（普通会话一致，影响很小）。
- **客户端接管方案**：移除 `aria-disabled`/`disabled`/`data-unavailable` + 原生 `stopPropagation` 拦截 React 合成事件 + Tooltip bubble `display:none` + MutationObserver rAF 保活——低风险；依赖官方 DOM 结构（`data-chat-anchor-key`、Branch 按钮 zh/en 文案），DSH 更新可能失效需维护。

## 七、归档机制查证（2026-08-09 补充）

`ctx.workspace.archiveSession(id)`（`packages/workspace/workspace/src/index.ts:204`）实际只做一件事：**把 sessionId 追加进 `archivedSessionIds` 持久化集合**（幂等：已归档直接返回；未知 id 抛 `WorkspaceUnknownSessionError`）。

归档效果：
| 维度 | 归档后 |
|---|---|
| 左侧列表/分组视图 | 消失（唯一的可见变化） |
| 会话日志文件（JSONL） | 原封不动 |
| workspace 记账（席位/顺序） | 保留（取消归档恢复原位置） |
| 内存 live agent | 不动（正在跑的回合照常完成） |
| 持久化/重启 | 仍在，带归档标记 |
| 数据销毁 | 完全不销毁 |

**归档 = 纯视图层隐藏 + 可逆收藏，零数据操作**（类似微信"折叠群聊"）。官方无会话级"真删除"API，归档 ≠ 删除。

## 八、会话裁剪方案（fork + archive，2026-08-09 补充）

需求：一个会话很多轮，想"删除第 N 轮之后的轮次"。

- **官方存储不允许截断**：append-only（"Flushed events are never rewritten"）、崩溃只关闭不截断、08-02 决策明确否决"在消息处截断事件日志"（截出的前缀可能含未结束 step/悬空工具调用，非结构完整轮次）。
- **语义裁剪（合规）**：`fork 到第 N 轮` → 子会话 = 只有前 N 轮；`archiveSession(旧会话)` → 旧会话从列表消失、数据完整保留可恢复。官方机制组合、零风险、可逆。
- **走私截断（不推荐）**：直接改写 JSONL 会破坏 live 内存同步、next-seq 记账、崩溃恢复（未关闭轮次自动补 closers）、检查点/投影缓存、运行中回合——"能改但必出鬼"。
- **实现**：书签模块二期加 `trim`（fork + archive 一步，`forkSession` 已有 + 调 `ctx.workspace.archiveSession`）。**待用户拍板**。

## 九、历史修改（AI 回复/用户提问）不可行性与合规替代（2026-08-09 补充）

**官方规则下修改历史结构性不允许**，四层证据：
1. 事件类型全集（`core/session/src/types.ts`：turn/start、user/message、assistant/chunk、assistant/message、step/start、step/end、tool/call、tool/result、turn/end、request/header、request/context、subagent、todo/write、legacy）**无任何修改/删除历史消息的事件类型**；
2. append-only（flush 后永不重写）；
3. 07-31 决策移除 user 编辑 stub，写明重新引入需"client 变异 + host 处理已消费该消息的轮次"两能力一起落地；
4. 08-02 决策否决截断事件日志。

**强制实现 = 越权改磁盘 JSONL**，牵动：
- 事件文件：改后必须 balanced（轮次配对完整）、seq 连续、JSON 合法，否则 load 拒绝；
- live 内存 Session 事件数组同步（无官方 API，只能 hack）；
- 派生状态失效：requestHeader 折叠、检查点缓存、token meter、上下文投影缓存、revision；
- 官方校验器：中段 seq 缺口拒绝、repair、崩溃恢复、版本 shape upgrade（如 pre-identity 消息迁移）；
- 模型记忆错乱：改后下次回合上下文基于新历史，但模型已"见过"旧回复（缓存/检查点）→ 隐性矛盾。

**合规替代（官方预留语义）**：
- **「编辑重发」**：官方 08-06 决策原话"从自己的提示词重问需要'切在消息之前 + 预填输入框'，是另一个 Host 操作"——即新回合承接，不改历史。插件 DOM 注入可实现（用户消息下加按钮 → 预填输入框 → 发送）。**建议书签二期，待用户拍板**。
- **改 AI 回复**：fork 后在分支纠正 / 继续对话纠正，历史保留可追溯。

## 十、书签 fork 确认弹窗排查记录（2026-08-09 补充）
