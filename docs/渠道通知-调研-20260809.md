## 一、背景与需求

用户使用 DSH 的方式：本机 GUI（dsh web）+ 多会话协作 + 外部 COI（grok/codex/kimi/zcode）派发任务。任务完成后用户可能不在电脑前——希望 AI 完成任务后通过 IM 渠道（QQ/飞书/微信/企业微信）主动推送一条通知，让用户知道"完成了"。

现状：
1. 4 个渠道插件（dsh-feishu/dsh-qqbot/dsh-weixin/dsh-wecombot）只做**入站聊天**（用户在 IM 里和 AI 对话），没有"AI 主动外发通知"的能力出口——所有发送入口都是插件内部私有方法。
2. memory-evolve 的 COI 调度已有**外部命令通知**（coiNotifyCommand：任务完成时 spawn shell 命令，支持 {taskId}/{coi}/{status}/{summary} 占位符），但它通知的是"外部程序"（如 pushplus/短信网关脚本），不是 4 个 IM 渠道。
3. 缺口：AI（GUI 会话或 COI 任务）完成工作后 → 无法主动把"我干完了"推到用户的 IM。

## 二、现状调研（源码级结论，2026-08-09 实锤）

### 2.1 4 个渠道插件是同一套架构（官方系，本地活跃维护）

| 插件 | 目录 | client | 协议/传输 | state 文件 |
|---|---|---|---|---|
| dsh-feishu | ~/.dsh/plugins/dsh-feishu | feishu-client.js | 飞书官方 WebSocket 长连接 | ~/.dsh/feishu-state.json |
| dsh-qqbot | ~/.dsh/plugins/dsh-qqbot | qq-client.js | QQ Bot API v2（C2C+群@） | ~/.dsh/qqbot-state.json |
| dsh-weixin | ~/.dsh/plugins/dsh-weixin | weixin-client.js | 微信 iLink Bot API（HTTP 长轮询） | ~/.dsh/weixin-state.json |
| dsh-wecombot | ~/.dsh/plugins/dsh-wecombot | wecom-client.js | 企微 AI Bot WebSocket 网关 | ~/.dsh/wecombot-state.json |

共同点（源码确认）：
- 全部 `export const inject = ['agents', 'commands']`，pure host plugin，**没有 provide 任何 cordis 服务、没有 HTTP API、没有文件接口**——发送能力完全私有。
- apply(ctx, config) 里创建 client + AgentBridge；`client.on('message')` → `bridge.handleMessage(message)`（入站驱动）。
- 配置文件在 `~/.dsh/profiles/web/cordis.patch.yml`（insert 列表），**4 个渠道插件全部只配了凭据，ownerIds 均未配置**（见 2.4）。
- 4 个插件都有独立 git 仓库、最近（8/9）还在更新——是本地可改的活跃插件，改造可行。

### 2.2 发送入口（唯一两个，均为私有方法）

**入口一：AgentBridge.sendToChat(sessionId, content, opts)**（如 feishu agent-bridge.js:709）
- 按 DSH 会话 id 查 `this.chats` Map（sessionId → {kind, id, userId}）→ 调 client.sendText
- ⚠️ chats Map **只在收到入站消息时 set**（handleMessage 里），且**不持久化**（state 文件只有 generations/bindings/seenMessages；chatKey 如 `p2p:oc_xxx` 可从 generations keys 重建，但需要解析）
- 语义是"给某个渠道会话回消息"——适合渠道自身回复，不适合通用通知

**入口二：Client.sendText(chat, content, opts)**（feishu:607 / qq:554 / weixin:450 / wecom:538）
- 参数 chat = `{kind, id}`，与是否收到过消息**无关**——只要知道 chatId 就能主动发
- 各渠道返回 `{ok, error?, messageId?}`，有超长分片（chunkText）+ 重试
- 各渠道主动发送能力：
  - **飞书**：sendMessage API，receive_id_type 自动判断（id 以 `ou_` 开头 = open_id，否则 chat_id）；tenant token 由 ensureToken 自动管理。机器人给用户发消息需用户添加过机器人。**支持主动发** ✅
  - **QQ**：官方 API v2 C2C 消息（openid），支持主动发（机器人向聊过天的用户发）✅
  - **微信 iLink**：发送必须回显对方最新 context_token（client.contextTokens Map，**持久化在 weixin-state.json 的 ilink.contextTokens**，重启可恢复）；无 token 时 sendChunk 遇 session expired 会**降级重试一次**（"degraded but accepted"，weixin-client.js:472）。⚠️ **主动发可行，但目标必须与机器人有过交互**（有 context_token），否则大概率失败
  - **企微**：sendText 优先 reply 模式（aibot_respond_msg，群聊必需），DM 无回复上下文时走**主动发送** aibot_send_msg（chatid）——代码注释明言支持主动 DM ✅

### 2.3 各渠道实际使用痕迹（state 文件实拍）

- feishu-state.json：1 个 p2p chat（`p2p:oc_0cb8...`），有 bindings 绑定到 session-b0b73145…（用户与飞书机器人聊过）
- weixin-state.json：1 个 c2c（`c2c:o9cq...@im.wechat`），带 context_token
- qqbot-state.json / wecombot-state.json：存在（有 generations 结构）

→ 用户每个渠道都真实用过至少一个对话；「最近交互 chat」作为默认通知目标是可行的。

### 2.4 「通知给谁」的数据现状

- 各插件 config 有 ownerIds（stringList 解析，逗号分隔）：飞书=openid、QQ=QQ 号/openid、微信=uid、企微=userid。**但 cordis.patch.yml 中 4 个插件全部未配置**——需要用户补配，或走别的目标来源。
- ⚠️ 语义差异：ownerIds 是**用户 id**，而 sendText 需要 **chat id**。飞书 open_id 可直接当 receive_id（receive_id_type=open_id）；QQ C2C 也用 openid；微信 uid 就是 chat.id；**企微 aibot_send_msg 要 chatid（会话 id），不是 userid**——ownerIds 不能直接转 chatId，需要渠道插件内部处理（用最近交互 chat 或用户补 notifyChatId）。
- 另一个来源：各插件 bridge.chats Map（内存）与 state 文件 generations keys——「最近交互 chat」最贴合"通知给刚才聊天的那个人"。

### 2.5 memory-evolve 现有通知雏形（可复用的触发时机）

- `makeNotify(commandTemplate)`（lib/coi/index.js:78-106）：任务终态时 `spawn('sh', ['-c', template])` 执行外部命令；{summary} 走环境变量 DSH_COI_SUMMARY 防命令注入（COI 输出不可信）。
- 触发点：scheduler.js:416 任务完成/失败时 `this.notify({taskId, coi, status, summary})`（try/catch 包裹，通知失败不影响任务）。
- 启示：**COI 任务完成的自动通知挂点已经存在**，扩展渠道通知只需在 notify 回调里加一条发送路径（或新增独立配置）。

### 2.6 架构约束（cordis 服务访问）

- 插件只能访问 `export const inject` 静态声明列表里的服务，未声明读 ctx.xxx 抛 "cannot get property 'xxx' without inject"（vendor/cordis/src/reflect.ts:144 实锤）。
- memory-evolve 是核心插件（inject=['tools','systemPrompt','agents','workspace','sessionTitle','sessionPersistence','settings','llm']，lib/index.js:59），**不能把 4 个可选渠道插件声明成硬依赖**（渠道插件可能被禁用/卸载，硬依赖会崩核心）。
- ctx.inject 动态注入历史踩坑：时序不可靠、工具可能不注册、产生 failed 插件实例（本项目关键记忆 2026-08-08）——不推荐。
- 关键事实：**memory-evolve 与 4 个渠道插件同进程装配**（同一 web profile 的 cordis.patch.yml insert 列表）→ 同进程共享 globalThis，全局注册表方案可行（见方案 A）。

## 三、候选方案对比

### 方案 A：渠道插件注册「发送能力」到全局注册表（推荐 ⭐）

渠道插件在 apply() 时把自己的发送函数挂到 `globalThis.__dshChannelNotify`（如 `{ feishu: (chat, content, opts) => client.sendText(chat, content, opts) }`），dispose() 时移除；memory-evolve 的 de_notify 工具执行时读注册表调用。

- ✅ 零网络、零延迟、同进程直接调用；渠道没装/禁用 → 注册表无该项 → 工具如实报"渠道不可用"
- ✅ 松耦合：memory-evolve 无任何渠道硬依赖；渠道插件侧改动极小（apply +5 行、dispose +3 行，不碰业务逻辑）
- ✅ 无端口/鉴权/文件竞态管理
- ⚠️ 要改 4 个渠道插件（各自 git 仓库，需用户同意；可分支开发、独立提交，插件更新合并时注意保留）
- ⚠️ globalThis 键名加 `__dsh` 前缀防冲突；HMR 重载时 dispose 清理要写对
- ⚠️ 插件不在同一进程时失效（当前架构下不存在此情况）

### 方案 B：渠道插件开本地 HTTP loopback 端口

每插件开 127.0.0.1:88xx/notify + 共享 token 鉴权；memory-evolve fetch 调用。

- ✅ 跨进程松耦合、有 HTTP 响应可回执
- ❌ 每插件一份 HTTP 服务 + 端口管理 + 鉴权设计 + 4 份实现，复杂度最高
- ❌ 当前渠道插件与 memory-evolve 同进程，用不上跨进程优势——**过度设计**

### 方案 C：共享文件队列

memory-evolve 写 ~/.dsh/notify-queue/xxx.json，渠道插件 fs.watch/轮询取走发送。

- ✅ 零网络、实现最简单、插件间零代码依赖
- ❌ 延迟（轮询间隔）、失败反馈弱（无回执链路）、多插件并发写读竞态、文件残留
- ❌ 仅为绕过"不能 inject"而付出，不如 A 直接

### 方案 D：memory-evolve 直接实现 4 个渠道 API

- ❌ 重复实现登录/长连接/轮询/协议，工作量巨大；凭据要从渠道插件 config 复制（维护双份）；微信 context_token 状态在 client 内存（外部拿不到，虽 state 文件有但要重复维护）
- **彻底否定**

### 结论

**推荐方案 A（全局注册表）**：改动面最小、语义最直接，且完全符合"渠道插件提供能力、memory-evolve 提供工具"的职责划分。B/C 的松耦合优势在当前同进程架构下无意义。D 否定。

## 四、工具设计（给用户拍板的清单）

### 4.1 工具形态

| 拍板点 | 选项 | 说明 |
|---|---|---|
| 工具名 | `de_notify`（推荐）/ `notify` / `channel-notify` | 沿用 de_ 前缀惯例（de_broadcast/de_session/de_coi_*） |
| 参数：渠道 | `channels: 'feishu'\|'qq'\|'weixin'\|'wecom'\|'all'`（可多选） | 默认 'all'=所有已注册渠道 |
| 参数：内容 | `content: string`（必填） | 消息正文，长度上限按各渠道分片（4000 字符内建议） |
| 参数：目标 | `target`（可选）：`owner`（ownerIds）/ `last`（最近交互 chat）/ 直接给 chatId | **需拍板默认值**（见 4.2） |
| 回执 | 工具输出逐渠道报告 `{ok, error?, messageId?}` | 如实展示失败原因（如微信无 context_token） |

### 4.2 「通知给谁」默认目标（需拍板）

现状：4 渠道 ownerIds **全部未配置**；但每个渠道都有真实交互 chat（state 文件可查）。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| ① 最近交互 chat（推荐一期） | 通知到"该渠道最近一次聊天的对话"（从渠道插件注册表暴露 `recentChat()`，读内存 chats Map + state 文件兜底） | 零配置、语义直观（"发到刚才那个聊天"） | 若用户从没在该渠道聊过 → 渠道不可用 |
| ② 配置 notifyChatId | memory-evolve 配置里手动填各渠道 chatId（如 `feishu: p2p:oc_xxx`） | 明确可控 | 需要用户找 chatId、换聊天要改配置 |
| ③ ownerIds 补配 | 用户把各渠道 ownerIds 填进 cordis.patch.yml，插件内部做 userId→chatId 转换 | 语义稳定（"永远发给这个人"） | **企微 userid→chatid 无现成映射**（aibot_send_msg 要会话 chatid，需插件内部维护）；QQ 要 openid 不是 QQ 号；都得用户现查 |
| 组合（推荐） | 默认 = 最近交互；target 参数可显式指定 | 灵活 | 一期实现量略增 |

### 4.3 触发方式（需拍板）

| 选项 | 说明 |
|---|---|
| ① 纯手动工具（一期最小） | AI 完成任务后自己决定调用 de_notify 发通知（任何任务通用，模型自主） |
| ② COI 完成自动通知（推荐一并做） | 复用 scheduler.js:416 的 notify 回调：新增配置 `coiNotifyChannels`（如 `feishu,qq`），任务完成时自动发"任务 xxx 已完成"；与现有 coiNotifyCommand（外部命令）互不冲突，可并存 |
| ③ 两者都要（推荐） | 自动（COI 任务）+ 手动（普通会话任务），共用同一发送内核 |

### 4.4 配置与开关（需拍板）

- 独立模块化：建议按项目惯例独立装配（独立开关 notifyEnabled 默认关？或默认开但渠道未注册时报错），**不借 COI 开关**（2026-08-08 教训：独立领域独立开关）。
- 配置存哪：memory-evolve 插件 config（~/.dsh/profiles/web/cordis.patch.yml 的 memory-evolve 项）或运行时配置（~/.dsh/memories/…/notify.json，GUI 可改）——后者与 COI 运行时配置同款，推荐。
- 发通知是否需要用户确认（防刷屏）：建议加"每回合最多 N 条"或"仅任务完成时"语义，拍板决定。

## 五、风险与边界（写进工具说明/文档）

1. **微信 iLink 特殊性**：主动通知目标必须与机器人有过交互（context_token 存在）；没有则降级重试一次、可能失败——工具必须如实返回失败原因，不能假装成功。
2. **企微群聊**：aibot_respond_msg 必须 reply 入站消息（req_id），主动通知**只能走 DM**（aibot_send_msg chatid）；目标为群时需有 replyTo 上下文，通知场景默认只支持 DM。
3. **飞书**：机器人给用户发消息要求用户添加过机器人/机器人有发消息权限，否则 API 报错（code≠0）——如实返回。
4. **ownerIds 未配置**：一期用"最近交互"兜底，不依赖用户补配；ownerIds 作为二期可选项。
5. **渠道插件改造**：4 个插件各加一个注册钩子（全局注册表 + 可选 recentChat() 暴露），需用户同意改独立仓库；建议渠道插件侧独立分支提交、与插件自身更新合并时保留。
6. **通知内容安全**：COI summary 走环境变量防注入的教训同样适用——渠道通知的 content 是普通字符串参数（工具参数天然结构化，无 shell 注入面），但要注意长度分片与换行处理。
7. **频率控制**：AI 可能重复发通知（每回合结束时都发）——工具 description 里约束"仅任务完成/重要节点时发"；可加可选 `quiet` 语义由模型判断。
