## 一、背景与痛点

同一个工作空间（工作目录）下可能同时有多个 DSH 会话并行工作，冲突高发：

1. **文件冲突**：两个会话同时修改同一个文件（edit/write 互相覆盖）
2. **git 状态冲突**：一个会话 commit/rebase/checkout 时，另一个会话正在改工作区文件
3. **服务冲突**：一个会话重启服务/占用端口时，另一个会话正在依赖该服务
4. **其他资源冲突**：同一目录结构变更、配置文件互踩等

现状：会话之间没有任何资源占用认知，冲突发生后靠事后发现（git diff / 文件被覆盖 / 服务挂掉），损失已经造成。用户痛点原话："如果同一个工作空间只有一个会话在进行，任务只能变成串行"——目标是在**安全的前提下保持并行**。

---

## 二、目标与范围

**目标**：让同工作区多会话并行时，对共享资源的写入"事前知晓、写前知晓、冲突定向提醒、事后可查"。

- 一期（用户拍板范围）：
  - 资源锁：声明（工具）+ 自动登记（监听写操作）+ TTL + 释放
  - **软模式写前感知**：检测到冲突时不拦截，但通过 post-execute 向写入方注入警告上下文 + 可选通知占用方
  - 状态查询工具：查"谁在干什么、锁了哪些文件"（无参 = 工作区活动概览）
  - **活动感知**：工作区活跃会话 ≥2 时快照注入一行活动概览（小开关，可选）
  - 冲突定向通知（复用广播通道）
- 二期（暂缓，用户拍板 git 互斥不做——让 AI 自己注意）：
  - 服务操作互斥（重启/端口占用声明）
  - 事后检测（回合结束对比 mtime，发现"我改的文件被动过"）
  - 客户端「工作区状态」面板
- 已砍（用户拍板）：git 元操作互斥（git commit/rebase 等让 AI 自己觉）；一期面板

**明确不做**：不做强制串行化（所有会话排队）；不锁读操作（读不产生冲突）；不锁不同文件（保持并行度）；**一期不做硬拦截（信任 AI，先软模式观察）**。

## 三、用户方案评估（为什么"广播"和"注册表"都不够）

### 3.1 方案 A：开工广播（de_broadcast 一对多）

任务开始时广播"我要做什么、改什么文件、什么影响，请大家知晓"。

- ✅ 优点：主动、无遗忘（对方看到了就是知道了）、能协调意图（"我要重构公共组件，大家别动"）
- ❌ 问题：
  1. **噪音**：全员广播，大多数人无关（用户已指出）
  2. **时效性**：AI 是回合制实体——广播到达时对方可能 idle（无人消费），或正在跑自己的回合（忙完才看到），**消息到达永远有延迟窗口，而冲突发生在写入那一刻**
  3. **声明 ≠ 实际**：AI 开始时说改 A、B，执行中可能改到 C、D（模型中途改计划是常态），广播覆盖不了计划外改动
  4. **软约束**：收到广播的 AI 正在改同一文件时并不会停下，只是"知晓"

### 3.2 方案 B：注册表工具（声明 + 查交集）

注册工具记录"自己现在什么时间、正在做什么、将有什么影响、要改什么文件"；其他会话要改文件时调用查询工具取交集。

- ✅ 优点：结构化、文件级精确、零噪音、交集语义正好对（只关心相同文件）
- ❌ 问题：
  1. **遗忘**（用户已指出）：没有 AI 会主动想起来查
  2. **登记完整性依赖自觉**：AI 忘了登记，表就不准，查了白查
  3. **TOCTOU 竞态**：查的时候没人占，写的时候别人刚好开始写
  4. **僵尸条目**：任务完成不清理，表越积越脏

### 3.3 盲点补充（用户方案之外）

1. **检查点应该在"写入那一刻"，而不是"开工那一刻"**——只有把检查放到写入动作本身，才能覆盖 AI 中途改计划的情况
2. **工具面差异**：DSH 里 AI 改文件有两条路——`edit`/`write` 工具（路径是结构化参数，可解析）和 `bash` 命令（自由文本，无法可靠解析）。任何"自动解析目标文件"的方案对 bash 无效
3. **事后损坏**：即使防得再好，冲突仍可能漏网（人手动改、跨进程、绕过检查），需要事后检测兜底

### 3.4 结论

通知解决"主动"，注册表解决"精确"，但都缺"强制"。**用户拍板（2026-08-09）：一期采用软模式——先信任 AI**。软模式成立的前提是"AI 看得见彼此"：活动感知（快照一行）+ 主动查询（de_ws_status）+ 冲突时双方知情（post-execute 警告注入 + 定向通知）。硬拦截（pre-execute deny）保留为开关项，观察软模式效果后由用户决定是否升级。

## 四、关键技术验证（源码级结论，2026-08-09 实锤）

在 DSH 快照源码（`packages/fs`、`packages/core/tools`）中逐项验证：

### 4.1 `fs/write-intent` / `fs/edit-intent`：被核心 fs-policy 独占 ❌

- 定义：`packages/fs/fs/src/index.ts` — `'fs/write-intent'(target, actor, next)` waterfall
- 调用点：`packages/fs/tool-fs/src/write.ts:111` — `ctx.waterfall('fs/write-intent', target, exec, () => undefined)`（undefined = 无条件放行）
- **关键发现**：`packages/fs/fs-policy/src/index.ts` 注释明言——"**occupy the single decision slot — do NOT call next()**"。fs-policy 是核心包、先注册、不调 next 截断链，**插件的 listener 在它之后永远不会被调用**。
- 结论：**插件无法在 fs 意图层拦截**（除非改造 DSH 核心，不做）。

### 4.2 `fs/observed`：emit 型，插件可监听 ✅（自动登记通道）

- 定义：`'fs/observed'(target, version, actor)` — emit（fire-and-forget）
- 调用点：`write.ts:122` 每次成功写后 `ctx.emit('fs/observed', target, outcome.version, exec)`；`edit.ts:141`、`read.ts:167` 同理
- **关键价值**：`actor = exec`（ToolExecution），可从中拿到 `exec.agent` → sessionId。**插件监听 fs/observed 就能自动知道"哪个会话写了哪个文件"——不需要 AI 自觉登记！**
- 结论：**登记通道 = fs/observed 监听 + exec.agent.sessionId**

### 4.3 `tools/pre-execute`：官方推荐的扩展点，可 deny ✅（强制拦截通道）

- 定义：`packages/core/tools/src/index.ts:137` — `'tools/pre-execute'(exec, next): Promise<PreToolDecision>`
- 官方定位：`packages/core/agent-loop/README.zh.md` — "沙箱、权限、计划模式：使用 `tools/pre-execute` 提供**可扩展的拒绝／询问**"
- 决策类型（`index.ts:550`）：
  ```ts
  type PreToolDecision =
    | { kind: 'allow' }
    | { kind: 'deny'; reason: string }   // materialize an error → AI 在工具结果里看到拒绝原因
    | { kind: 'ask'; reason?: string }   // 走审批服务
  ```
- **不调 next() = veto**；调 next() = 放行链下一位
- 核心包无占用者（agent-loop 只在自己的测试里演示），**是留给插件的扩展点**
- 结论：**拦截通道 = tools/pre-execute，对 write/edit 返回 { kind:'deny', reason }**

### 4.4 `ToolExecution.agent` → sessionId ✅（能识别"谁在写"）

- `index.ts:298` — `ToolExecutionInput.agent?: Agent`（"The agent on whose behalf the call runs (set by the agent loop)"）
- agent 有 sessionId（本项目 de_session 模块一直在用 `ctx.agents.get(sessionId)`）
- 结论：拦截/登记时都能拿到**调用方会话 ID**

### 4.5 工具参数可解析性（覆盖范围边界）

| 写路径 | 路径是否可解析 | 拦截方式 |
|---|---|---|
| `write` 工具 | ✅ `args.file_path` 结构化 | tools/pre-execute 直接解析 |
| `edit` 工具 | ✅ `args.file_path` 结构化 | 同上 |
| `bash` 命令 | ❌ 自由文本，无法可靠解析 | 只能靠声明（de_ws_declare）+ 二期 git/服务命令正则匹配（git 是半结构化命令，可正则） |
| 外部 CLI（codex/grok 等 COI） | ❌ 插件不可见 | 靠 git 事后检测兜底 |

### 4.6 验证结论汇总

```
拦截点：tools/pre-execute（官方扩展点，deny 语义完整）✅
登记点：fs/observed（emit 监听，exec.agent 拿会话）✅
识别方：ToolExecution.agent.sessionId ✅
不可行：fs/write-intent（fs-policy single-slot 独占）❌ → 不需它，上层已覆盖
盲区：bash / 外部 CLI 写入 → 声明 + 兜底检测
```

| 复用项 | 方式 |

## 六、方案详细设计：三层防护

### 6.1 数据模型：锁存储

```
<memoryDir>/ws-coord/
└── <workspace-hash>/locks.json        # 工作区锁表（§ 无，纯 JSON 原子写）
```

```jsonc
{
  "version": 1,
  "locks": [
    {
      "id": "lk_abc123",
      "sessionId": "session-xxx",        // 占用方会话
      "kind": "file" | "service",        // 文件锁 / 服务锁
      "target": "src/lib/api.js",        // 文件路径（realpath 归一化）或服务名
      "note": "重构 API 层，涉及导出签名变更", // 干什么、什么影响（AI 声明/自动生成）
      "startedAt": 1754700000000,
      "expiresAt": 1754703600000,        // TTL，写操作自动续期
      "source": "declared" | "observed"  // 声明 / 自动登记（fs/observed）
    }
  ]
}
```

### 6.2 第一层：资源锁（声明 + 自动登记）

**入口 1：声明（软，AI 主动）** —— 工具 `de_ws_declare`
- AI 开工时声明："我要改 src/lib/api.js、src/types.ts；重启 dev 服务"
- 带 note（做什么/什么影响）和 TTL（默认 1 小时，上限 24h）
- 同时可附带 git/服务操作声明（二期）

**入口 2：自动登记（硬，不靠自觉）** —— 监听 `fs/observed`
- 每个会话每次成功写文件（write/edit 工具），插件自动把 `(sessionId, realpath(targetKey))` 记入锁表，source=observed，刷新 TTL
- **效果：AI 实际写了什么，锁表就有什么**——解决"声明 ≠ 实际"

**生命周期**
- 续期：每次 fs/observed 写操作刷新该会话锁的 expiresAt；de_ws_declare 可显式续期
- 释放：`de_ws_release`（AI 主动）/ 回合结束（监听 `agent/turn-stopping` 清理该会话 observed 锁）/ TTL 超时 / 会话空闲超时（复用 presence idle 数据）
- 僵尸清理：模块启动时 + 每次查询时惰性清理过期锁

### 6.3 写前感知（软模式，用户拍板一期；硬拦截为开关项备用）

**软模式：检测冲突但不打断**，让双方知情、全程留痕：

```
工具调用（write/edit/bash…）到达 tools/pre-execute
  │
  ├─ exec.name ∉ {write, edit} → next() 放行（bash 普通命令不检测）
  │
  ├─ 解析目标路径（exec.arguments.file_path → realpath 归一化）
  │     │
  │     ├─ 无锁 / 锁的 sessionId == 当前会话 → next() 放行（无事发生）
  │     │
  │     └─ 锁的 sessionId ≠ 当前会话（他人占用）
  │           ├─ 软模式（默认）→ next() 放行，但：
  │           │    ① tools/post-execute 附加警告上下文（additionalContexts）：
  │           │      "⚠️ 你写入的文件 src/lib/api.js 正被会话 A 占用（正在做：重构 API 层…）。
  │           │       如非有意，建议先 de_ws_status 查看详情或与其协商。"
  │           │    ② 可选通知占用方（notifyConflict 小开关）："会话 B 刚写入了你的文件 F"
  │           │    ③ 冲突记录写入 ws-coord 日志（de_ws_status 可查，事后留痕）
  │           └─ 硬模式（enforceWrite 小开关打开）→ 返回 { kind:'deny', reason:
  │                 '文件 src/lib/api.js 正被会话 A 占用（正在做：重构 API 层…，剩余约 40 分钟）。
  │                  建议等待其释放，或用 de_ws_status 查看详情。' }
  │
  └─ 完成
```

要点：
- **软模式不打断 AI 工作流**（信任 AI），但 AI 下一轮上下文里就能看到警告（additionalContexts 进上下文）
- 警告注入用 post-execute 的 additionalContexts（UserMessage 追加），与 ⚡立即注入的插话机制同源
- 硬模式（deny）保留为开关项，观察软模式效果后用户可随时切换
- 同会话自锁放行（AI 连续写自己的文件不被打断）
- agent 为 undefined 的调用（SDK/非 agent 发起）跳过检测
- 性能：锁表内存缓存，pre-execute 同步 O(1) 查询，无 IO

### 6.4 第三层：冲突定向通知（最小噪音）

- **原则：平时不说话，真冲突才说话**（解决广播噪音）
- 触发点：① 拦截发生时（deny 的同时）；② 声明与现有锁重叠时（de_ws_declare 返回冲突清单）
- 通知对象：**只通知冲突双方**（点对点，非全员）：
  - 被拦方：deny reason 已自带信息（工具结果即通知，无需额外消息）
  - 占用方：可选——"会话 Y 想写你的文件 F 被拦截了"，让对方知道有人等着（默认开，帮助对方主动收尾；小开关可关）
- 通道：复用广播 store send（桥接）；广播未启用 → 不额外通知（deny reason 已闭环）

### 6.5 兜底与边界（git 互斥已砍，用户拍板"让 AI 自己注意"）

**git 元操作互斥**：❌ 已砍（用户拍板，2026-08-09）——git commit/rebase/checkout 等不做插件级互斥，让 AI 自己注意。可通过声明 note 告知他人（"我要 commit，大家注意"），配合活动感知快照段让其他人知晓。

**服务操作互斥**（二期候选）：de_ws_declare 支持 services 声明（重启 dev / 占用端口 3000）；他人声明了该服务 → 冲突检测命中。

**事后检测**（二期候选）：监听 `agent/turn-stopping`：会话回合结束，对比该会话锁表中文件的 mtime 快照——发现"我写过的文件在我回合外被别人改过" → 写入该会话收件箱提示人工核对合并；依赖 git status 快照对比更准（可选）。

### 6.6 完整时序示例（软模式）

```
时间线：会话 A（重构 api.js）与 会话 B（改 types.ts 中碰了 api.js）并行

T1  A: de_ws_declare { targets:[{path:'src/lib/api.js', note:'重构 API 层，导出签名变更'}], ttl:60 }
    → 锁表: [A → api.js (declared, expires 60min)]
T2  A: write src/lib/api.js → pre-execute 无冲突 → 放行
    → fs/observed → 自动登记 [A → api.js (observed)]，TTL 刷新
T3  B: write src/types.ts → 无冲突 → 放行（不同文件，并行不受影响）
T4  B: edit src/lib/api.js → pre-execute：api.js 被 A 占用 → 软模式放行
    → post-execute 注入警告："⚠️ api.js 正被会话 A 占用（重构 API 层）"
    → B 的 AI 下一轮看到警告 → 查 de_ws_status 或调整计划
T5  A: 收到定向通知（可选）："会话 B 刚写入了你的文件 api.js" → A 留意
T6  A 回合结束 → observed 锁释放；declared 锁保留到 TTL 或 A 主动 de_ws_release
T7  事后：de_ws_status 可查全部冲突留痕记录
```

### 6.7 活动感知（回答"AI 能否主动知道谁在跑、在干什么"）

**现状盘点**：
- ✅ 已有：`de_session status/list`（running/idle/offline + lastActiveAt）、`de_broadcast presence`（房间成员在线）——能回答"谁在跑"
- ❌ 缺口："在干什么"——会话状态只有 running/idle，没有任何任务意图信息

**补齐（本项目新增）**：
1. **`de_ws_status` 无参调用 = 工作区活动概览**：返回当前工作区所有活跃会话 + 各自声明（在做什么/锁了哪些文件/剩余时间）。AI 开工前主动查一次即知全局。
2. **活动感知快照段（小开关 `wsCoord.snapshot`，默认开）**：当工作区活跃会话 ≥2 时，快照注入一行：
   `【工作区活动】2 个会话并行中：A 重构 api.js / B 写测试。动共享文件前先 de_ws_status 查询占用`
   - 0~1 个活跃会话时不注入（零开销，克制原则）
   - 内容只含会话别名 + 声明摘要（固定格式，省 token）
   - 这就是软模式的"眼睛"：AI 每回合被动看到有人在干活，自然会谨慎；配合 de_ws_status 主动深查

## 七、工具设计（de_ws_* 前缀，防插件冲突）

### 7.1 `de_ws_declare` — 声明占用

```
参数：
  targets?: [{ path: string, note?: string }]      // 要修改的文件
  services?: [{ name: string, action?: string, note?: string }]  // 服务/端口（二期）
  ttlMinutes?: number                              // 默认 60，上限 1440
返回：
  declared: [...已登记条目]
  conflicts: [...与现有锁的重叠清单]（发现即提示，不含则空）
  message: 文本摘要
```

### 7.2 `de_ws_status` — 查询占用与工作区活动（交集）

```
参数：
  paths?: string[]      // 只查这些文件（交集语义：多个会话要改同一文件时用）
  sessionId?: string    // 只看某会话
  （无参 = 工作区活动概览：当前工作区所有活跃会话 + 各自声明/占用）
返回：
  locks: [{ sessionId, kind, target, note, startedAt, expiresAt, source }]
  active: [{ sessionId, alias, status, note, lockCount }]   // 活动概览（无参时）
  message: 文本摘要（含过期锁清理说明）
```

### 7.3 `de_ws_release` — 释放占用

```
参数：
  paths?: string[]      // 释放指定文件
  all?: boolean         // 释放本会话全部（回合收尾时）
返回：
  released: [...]
  remaining: [...]
```

## 八、开关体系（广播模块内子开关组，大开关 + 小功能开关）

> 用户拍板：大模块有开关，模块内小功能也有开关（仿 DSH UI 设置「综合」模式）；本功能默认关。

| 开关键 | 粒度 | 默认 | 控制什么 |
|---|---|---|---|
| `broadcastEnabled` | 广播模块 | 关 | 大开关——关闭时 wsCoord 子功能全部不注册 |
| `wsCoord.enabled` | 子功能组 | **关**（用户拍板） | 工作区协调整体（工具注册 + 事件监听 + 存储初始化） |
| `wsCoord.declareTool` | 功能 | 开 | `de_ws_declare` / `de_ws_release` 工具 |
| `wsCoord.statusTool` | 功能 | 开 | `de_ws_status` 工具（含工作区活动概览） |
| `wsCoord.autoRegister` | 功能 | 开 | fs/observed 自动登记（关掉则只有声明式锁） |
| `wsCoord.enforceWrite` | 功能 | **关**（软模式，用户拍板） | 硬拦截 deny；打开后软警告升级为硬拦截 |
| `wsCoord.notifyConflict` | 功能 | 开 | 冲突时给占用方发定向通知 |
| `wsCoord.snapshot` | 功能 | 开 | 活动感知快照段（活跃会话 ≥2 时注入一行） |
| `wsCoord.serviceGuard` | 功能（二期） | 关 | 服务/端口互斥 |
| `wsCoord.postDetect` | 功能（二期） | 关 | 回合结束事后检测 |
| ~~`wsCoord.gitGuard`~~ | ~~功能~~ | ~~砍~~ | ~~git 元操作互斥——用户拍板不做，让 AI 自己注意~~ |

> 说明：`wsCoord.enabled` 关 = 工具不注册、事件不监听、零开销；开但小功能全关 = 只初始化存储。

## 十一、风险与待验证点

| 风险 | 等级 | 说明与对策 |
|---|---|---|
| tools/pre-execute 是官方扩展点但未来可能变化 | 中 | 项目有 dsh-snapshot-merge 技能跟随快照；事件签名变更时按快照适配 |
| bash 写入无法解析 | 中 | 声明（de_ws_declare）+ 二期 git 正则 + 事后检测兜底；文档明示边界 |
| 外部 CLI（COI 任务）写入不可见 | 低 | 归 git 事后检测兜底；COI 任务一般独立目录或由主会话协调 |
| 路径归一化（相对路径 vs realpath） | 中 | 锁匹配统一 realpath；targetKey 是 local backend 的 realpath，天然一致 |
| 误伤（同文件不同区域） | 低 | 文件级粒度偏粗但安全优先；note 里写清区域可降低误伤；人工清锁兜底 |
| 性能 | 低 | pre-execute 同步内存查询 O(1)；fs/observed 是 fire-and-forget emit |
| fs-policy 单槽独占的教训 | - | 已确认不走 fs/write-intent；如未来需要文件系统层拦截，需给 DSH 提需求（扩展点） |
