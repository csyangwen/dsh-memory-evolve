# 会话书签/恢复点——DSH 分支机制调研（2026-08-09）

> 双人并行调研后综合：**Grok**（源码机制层，读 /Users/edgar/code/deepseek/test-csyangwen 源码）+
> **Codex**（设计层，数据结构 + 官方意图 + 业界先例）。本文件为综合结论，供立项决策使用。

## 1. 背景与目标

用户设想：在对话的**每一轮**打标签（书签），标签显示在 DSH 界面里，之后可**随意跳转到任一轮并创建新分支**——实现对上下文最精准的利用。此前疑问：官方为什么只允许从"最后一轮"创建分支？插件层能否实现"任意轮书签 + 跳转 + 分支"？

## 2. 核心结论（先看这个）

| 问题 | 结论 |
|---|---|
| 官方能否从任意轮分支？ | **能**——DSH 的 fork 在 Core/Host/Client 三层均已支持「任意已完成轮」前缀分支 |
| 那为什么 UI 看起来只能从最后分支？ | 限制是**按 `turn/end` 整轮切** + **UI 仅在轮尾 assistant 消息启用按钮**（产品层收敛），**不是核心层"只能从末尾分"** |
| 插件侧做"任意轮书签+跳转+分支"？ | **可行**——分支直接调已有 `session.fork({ sessionId, atSeq })`，无需改核心、无需手搓文件 |
| 书签存哪？ | 插件 sidecar（JSON 或 sqlite），存 `{ seq, label }`；不碰官方存储 |
| 跳转怎么做？ | `data-chat-anchor-key` 定位 + 必要时 `loadOlder` 拉历史窗口 |
| 续聊 = 分支？ | 是——"从此处新建分支"复用官方 fork，二级显式动作 |

## 3. 源码事实（Grok 调研）

### 3.1 fork 的完整数据流
- 官方 fork 能力在 **Core（session 服务）/ Host（RPC）/ Client（web）三层**都有实现，取数单位是**已完成轮次（turn/end）**：`session.fork({ sessionId, atSeq })` / client `sessions.fork`。
- 官方 Web 对**多轮中间轮**也可用（见 `apps/web/tests/chat-long-interactions.e2e.ts`）；按钮仅渲染在轮尾 content assistant 上（`apps/web/tests/message-actions.e2e.ts`）。

### 3.2 为什么"看起来"只能从最后分支
- 真正的限制不是"会话只能从末尾分"，而是：
  1. **整轮粒度**：只能从某个已完成的轮次（turn）切，不能从开放轮次或轮次中间的可见消息切开；
  2. **UI 收敛**：官方界面只在最后一条消息附近暴露分支入口，中间轮次的 fork 能力没做成入口（属于产品决策/未暴露，而非底层不可行）。

### 3.3 存储模型（Codex 补充）
- 官方存储是**每会话线性仅追加日志** + **子会话复制前缀** + `parentSession` 谱系指针——**不是单会话 DAG**。分支 = 复制到目标 seq 的前缀 + 新日志段。
- **模型历史可以由旧前缀重建**（转录片段齐全，seq 可定位）；但**文件、进程、数据库、网络副作用不能随 transcript 回滚**——这是"从任意轮分支"唯一的硬边界（分支后继续对话的模型状态没问题，外部副作用状态要自己处理）。

## 4. 插件侧实现方案（综合）

### 4.1 书签数据
- sidecar 存储：`~/.dsh/memories/bookmarks.json`（或 sqlite），结构建议 `{ sessionId, bookmarks: [{ id, label, seq, createdAt }] }`；
- 也可用 settings 或 merge 的 log-only 事件存 `{seq, label}`（不持久进对话历史，用户无感）；
- 书签所有权归源会话；子会话可显示"继承自父会话"的只读书签（`anchorSeq < seedLength` 时位于继承前缀）。

### 4.2 分支
- **始终复用官方 `session.fork({ sessionId, atSeq })`**——不做自己的 fork 存储，新会话自然通过 `parentSession` 出现在官方谱系树中。
- 删除书签不删除已创建分支；删除分支也不自动删书签（松耦合）。

### 4.3 跳转/定位
- 客户端用 `data-chat-anchor-key` 定位目标轮，必要时 `loadOlder` 拉历史窗口；
- UI 挂载点：`conversation.chat.turnTail`（每轮尾部操作区，放"★ 打书签"按钮）与 `conversation.view`（书签列表侧栏）槽位。

### 4.4 明确不做
- 工作区回滚、分支合并（多父关系）、自动 GC、修改官方日志格式——官方机制不支持，插件不承诺。

## 5. 实施路线（建议三阶段）

- **第一阶段**：每轮星标 + 书签列表 + 查看跳转（验证"历史定位"是否真被需要）
- **第二阶段**：书签上的"从此处新建官方分支"（复用 session.fork）
- **第三阶段**：父子会话继承书签、全局书签搜索、导入导出
- 暂不做：工作区回滚、分支合并、自动 GC、改官方日志格式

## 6. 业界先例对照（Codex 调研摘要）

ChatGPT（编辑历史消息）、Claude（对话分支）、Cursor（checkpoint/恢复点）、Git（commit/branch）、IDE debugger（断点）——共性结论：**"任意点回溯"的可行形态 = 轻量标记 + 定位跳转，续聊/分叉作为显式二级动作**，避免把需求升级成完整会话版本控制系统。与 4.4/5 的设计一致。

## 7. 风险与边界

1. 只能从**已完成轮次**打书签（开放轮次不可），这是 DSH 的硬约束；
2. 外部副作用（文件/进程/DB）不随分支回滚——书签跳转后继续对话时上下文是"当时的前缀"，外部世界是"现在"；
3. 官方 UI 未暴露中间轮 fork 入口——插件侧从客户端调用 fork 能力即可绕过 UI 限制（能力在，只是没有按钮）；
4. 需要验证 `session.fork` 的 atSeq 语义与书签 seq 的精确对齐（fork.spec.ts / api-proxy-fork.spec.ts 已有测试可参考）。

## 8. 结论

**立项可行，且实现路径清晰、无需改 DSH 核心**：书签 = 插件 sidecar `{seq, label}` + 客户端 turnTail 槽位打标/跳转；分支 = 复用官方 `session.fork`。建议按三阶段实施，先做第一阶段（星标+列表+跳转）验证需求，再做"从此处分支"。验证线索：`packages/core/session/tests/fork.spec.ts`、`packages/host/apiproxy/tests/api-proxy-fork.spec.ts`、`apps/web/tests/message-actions.e2e.ts`、`apps/web/tests/chat-long-interactions.e2e.ts`。
