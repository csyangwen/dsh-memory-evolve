# 用户情绪反馈记录 调研 v4（极简版，2026-08-10）

> 读者：插件维护者 / 后续开发者。本文记录「用户情绪/质量反馈记录」的最终设计。v4 采纳用户极简方案：**不建独立存储、不监听事件、不加规则引擎**——复用现有每轮 daily/project 日志写入通道，由 AI 顺手记录，按需分析。

## 1. 方案演变

- v1：独立模块 + `agent/inbox/inserted` 事件捕获 + 规则关键词判定 + JSONL 存储 + 独立工具。
- v2：多维分层（会话/项目/分支/分类树/模型/思考强度）+ 手动评分 + 能力画像（类数据库表）。
- v3：存储改 AI 友好 MD 条目式（用户拍板），其余同 v2。
- **v4（最终）**：用户指出过度工程化——情绪记录是低频数据、判定是语义工作、分析是按需动作，全部并入现有日志机制即可。

## 2. 最终设计（三层，零新增基础设施）

### 2.1 第一层：自动记录（每轮收尾纪律）

**机制**：修改 `lib/index.js` renderSnapshot 的纪律段（固定文本，不违反状态驱动稳定铁律），要求 AI 每轮收尾写 daily/project 时，若本回合**真人用户输入含明显情绪**，在日志条目末尾附一行固定模板：

```
【反馈】情绪:正面/负面 | 分类:一级/二级/三级 | 表现:好/不好（一句话）
```

规则：
- **中性/纯任务指令 → 不记录**（低噪音）；
- **仅记真人用户消息**——其他会话 AI 发来的指令（wake/广播）不记（AI 在对话中天然可分，无需 source 改造）；
- 情绪分档从简：**正面/负面两档**（可带强度词"强烈"），不做 7 档数值——AI 自然语言比数字更可靠、更一致；
- 分类：AI 自由写斜杠路径（如 `编程/后端/数据库`），一级参考列表（编程/文档/运维/数据分析/设计/通用）写入纪律段提示，二级三级自由；
- `【反馈】` 是**检索锚点**：分析时 `memory list target=daily filter=【反馈】` 拉取。

### 2.2 第二层：手动记录（用户触发，零工具）

用户直接说话（如"记一笔：文档类做得好"）→ AI 写：

```
【反馈·手动】分类:文档 | 表现:好
```

无需命令/工具/面板。与自动记录同处日志，`【反馈` 前缀可一并检索。

### 2.3 第三层：按需分析（无预聚合）

触发方式：用户主动说"分析一下最近的反馈" / 记忆审查时引导（可选，审查纪律加一句）。

流程：AI `memory list target=daily filter=【反馈】`（可 since/until 限定区间）→ 按分类聚合正负面 → 输出小结（哪类做得好/不好、趋势），可进一步转 `memory_suggest` 建议（走用户确认队列）。

## 3. 与 v3 方案的对比（为什么 v4 更好）

| 维度 | v3（复杂版） | v4（极简版） |
|---|---|---|
| 判定 | 规则关键词（糙）或 LLM 即时（贵） | AI 语境判断（准、零额外成本——每轮本来就要写日志） |
| 存储 | 新目录 + tag 行 MD + 分类字典 + 评分表 | 无新文件，就在 daily/project 日志 |
| 捕获 | 事件监听 + source 过滤 + subagent 跳过 | 无（AI 自己知道消息来源与身份） |
| 工具 | memory_feedback（list/summary/scores） | 无新增 |
| 分析 | summary 工具聚合 + 审查联动 + 二期报告 | 按需让 AI 读日志分析 |
| 代码量 | 新模块 500+ 行 + 工具 + 配置 | 纪律段文本 +（可选）审查提示一句 |

**关键认知**：情绪记录是**低频 + 语义 + 按需消费**的数据，三项特征都指向"AI 顺手记、需要时再分析"，而非程序化流水线。v3 把低频数据当高频数据设计了（事件监听/规则引擎/独立存储），是过度工程化。

## 4. 已知代价（诚实清单）

1. **依赖 AI 遵循纪律**：弱遵循模型可能漏记（与现有每轮写日志同款风险，属既有模式）；缓解=只记"明显情绪"，并可在审查时抽查补记。
2. **格式一致性**：AI 自由发挥可能写歪格式；缓解=模板极简固定、情绪仅两档、`【反馈】` 锚点统一。
3. **分析受上下文限制**：日志量大时 filter 检索即可（daily 按天分文件，since/until 限定区间），个人使用量无压力。

## 5. 实施范围（最终）

1. `lib/index.js` renderSnapshot 纪律段：新增情绪记录要求 + 固定模板文本（含一级分类参考列表、只记真人消息、两档情绪、`【反馈】` 锚点）；
2. （可选）审查纪律段加一句"分析近期反馈可转建议"；
3. 文档：本调研文档 + README 相关章节；
4. 无需：新模块/新工具/新配置/事件监听/wake source 改造/前端改动。

## 5b. v5 实施记录（2026-08-10 已落地，测试 329/329 通过）

按外援审查修正后落地（Codex+Grok 双审，综合结论见会话记录）：

| 项 | 落地内容 |
|---|---|
| memory 工具 `entries` 参数 | 一次调用批量写 daily+project（**仅限这两轨**，schema enum 与程序双重限制，防绕过 subagent 门禁/key 队列） |
| memory 工具 `feedback` 参数 | {sentiment(必填), category, quote, note, manual}；程序拼接【反馈】行（自动）或【反馈·手动】行（manual=true）；**daily/project 双轨生效**（用户拍板：分析可能不带 daily，项目视角要有） |
| 反馈行格式 | `【反馈】情绪:正面/负面 \| 分类:… \| 原话:"…" \| 表现:…`；字段清洗 \|、换行、§、引号；quote 强制截断 ≤20 字；category 缺省"未分类" |
| 分类双轨 | daily 写通用分层（编程/后端/数据库），project 写项目内分层（记忆模块/写入链路）——纪律段与 description 均写明 |
| output schema 闭合 | 新增 `multi: [{target, ok, message}]`；每项返回仅 {target,ok,message}；**顺带修复现存 bug：outcomeOnly 增剥 `removed`**（store.replace/remove 返回的 removed 字段此前超出 schema，additionalProperties:false 下会被模型 API 拒） |
| required 放宽 | `['action','target']` → `['action']`（entries 模式无需顶层 target）；execute 加兜底校验（缺 target 且非 entries → 明确报错） |
| 纪律段 | 每轮收尾改为**一次调用**（entries 含两轨）写 daily+project；真人消息有明显情绪时两条都带 feedback；中性指令/其他会话 AI 消息不带 |
| 工具 description | 追加"每轮收尾批量写"与"情绪反馈"说明段落 |
| 子代理变体 | 保持降级（仅独立成果写 1 条，一次调用） |

技术决策说明：
- feedback 在 schema 层仅必填 sentiment（category/quote/note 程序宽容缺省）——**选可靠性优先**：若全必填，模型漏填一个字段会导致整个调用被模型 API 拒，连带日志主体写不进去；缺省段不输出即可。
- `entries` 限两轨后 subagent gate 绕过问题自然消失（entries 项不可能是 memory/user）；key 轨不参与批量。
- 验证链：assertSupportedJsonSchema（parameters+output）→ 行为测试（13 项：批量/清洗/截断/拒非法轨/单轨/兜底/manual/回归）→ 全量测试套件 329/329。

## 6. 技术调研结论（v1-v3 沉淀，备查）

- `agent/inbox/inserted`（emit，live-only 不重放）是程序化捕获用户消息的挂载点——v4 不采用，但若未来做程序化捕获可复用此结论；
- `source.kind==='user'` 无法区分真人 vs 本插件 wake（wake 硬编码 user）；改 `{kind:'plugin'}` 可 100% 区分——v4 不需要，备查；
- `session.requestHeader().config` 可读 provider/model/reasoningEffort——v4 不需要，备查；
- DSH 官方 `packages/feedback`（/feedback 命令 → feedback/record 事件，log-only）——用户拍板不并入，备查；
- 快照段状态驱动稳定铁律约束不变（纪律文本固定，安全）。
